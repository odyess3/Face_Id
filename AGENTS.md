# Project activity reporting

Ody wants a detailed running record of both his work and the assistant's work in this project, including small steps such as looking through sources.

- Read `REPORT.md` at the start of project work and append an update before finishing each work session.
- Record requests, questions, source exploration, code reading, explanations, commands tried, edits, experiments, errors, fixes, decisions, checks and outcomes, even when a step seems small.
- For a source, record its title or URL when available, who looked at it, what they did with it and any reported takeaway or question. If no takeaway was supplied, say so rather than inventing one.
- Distinguish a link saved in a file from a source actually opened, read or tested. Do not claim Ody read something merely because its URL is present.
- Distinguish what Ody reports, what tools directly show, assistant actions, assumptions, proposals and verified results. Do not attribute an action to Ody based only on a Git author name.
- Record activity visible in the conversation and available tools only. This is not automatic monitoring of the computer, browser or work outside the chat. If Ody reports earlier work, add it retrospectively and identify the reported date or say that it is unknown.
- Preserve earlier entries. Correct inaccuracies explicitly. Historical entries are not proof of the current project state; verify the current owning files before relying on them.
- Use plain English and Europe/London dates. Avoid hyphens in ordinary phrases; preserve required syntax in code, file names and URLs.
- Keep useful detail without copying noisy output, secrets, raw student identifiers or unnecessary personal data from card images.
- Record local changes separately from commits and GitHub pushes. Do not automatically commit or push because the report was updated.
- Use relevant available skills for the actual task and follow Ody's requested learning pace. Reporting work alone does not authorise unrelated code or project changes.
